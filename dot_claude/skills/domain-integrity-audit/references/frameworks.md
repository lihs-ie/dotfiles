行列 (手順 4) で見つかった疑義の裏取りに、該当するものだけを選んで使う。

## 1. Requirements Traceability

ソフトウェア工学の Requirements Traceability Matrix (RTM) の応用。監査全体の背骨であり、
SKILL.md 手順 4 の行列そのもの。

**手順**: 理論 → 原理 → 必要な行動 → 必要な機能 → UI を一本の線でつなぐ。

**例 (スペースドリピティション)**:

| 層 | 内容 |
|---|---|
| 原理 | 忘却曲線・適切な復習間隔 |
| 必要な行動 | 復習日時を守る・忘れる前に復習する |
| 必要な機能 | 通知・今日の復習一覧・復習スケジューラ |
| UI | ホーム画面・通知導線・レビュー画面 |

**判定**: 「このボタンはどの原理を支えているのか?」まで遡れない機能はドメイン対応が弱い。

## 2. Conceptual Model Alignment

UX の概念モデル評価。**システムの概念モデル = 対象ドメインの概念**になっているかを確認する。
用語の表層一致ではなく、概念の構造 (何と何がどう関係するか) の一致を見る。

**例 (GTD)**: 本来の概念は「収集・整理・実行・レビュー」。アプリに「メモ・タグ・検索」しか
存在しないなら、概念モデルがずれている — メモは収集の劣化版であり、整理 (次のアクションへの
変換) とレビュー (定期的な棚卸し) に対応する概念がまるごと欠落している。

**手順**:
1. 理論側の概念とその関係を列挙する (手順 2 の正統用語集を使う)
2. アプリ側の概念 (画面・オブジェクト・操作) を列挙する
3. 対応表を作り、欠落概念・余剰概念・構造のずれを指摘する

## 3. Cognitive Walkthrough

UX 評価手法。ユーザーが**理論本来の実践プロセス**を踏むとき、一歩ずつ何を考えるかを追い、
アプリ上で迷わず実践できるかを評価する。

**例 (学習アプリ)**: 問題を解く → 間違える → 解説を読む → 理解する → 翌日復習する。
この各ステップで「次に何をすべきか分かるか」「正しい操作が最短導線か」を問う。

**手順**: 理論の推奨プロセスをステップ列に書き下し、各ステップで
(a) ユーザーは正しい行動を思いつくか、(b) その行動が UI 上で見つかるか、
(c) 実行後に進捗が理解できるか、を評価する。**誤った行動のほうが簡単な箇所**は重大所見。

## 4. Task Analysis

人間工学の分析手法。理論をタスクに分解し、各タスクへの支援機能の有無を確認する。

**例 (フェインマン・テクニック)**:

| # | タスク | 支援機能はあるか |
|---|---|---|
| 1 | 理解する | 教材ビュー? |
| 2 | 説明する | 説明を書く/話す場? |
| 3 | 詰まる | 詰まった箇所の記録? |
| 4 | 調べ直す | 資料への戻り導線? |
| 5 | 説明し直す | 改訂版の説明と差分? |

**判定**: 支援がないタスクはユーザーの自助に丸投げされている。理論の中核タスク
(この例では 2 と 3) の未支援は High。

## 5. Service Blueprint

UX 全体を俯瞰する。ユーザー行動 / 画面 (frontstage) / システム処理 (backstage) /
通知 / データベース を時系列に並べ、**どの層に抜けがあるか**を確認する。

理論の要求はしばしばユーザーに見えない層に落ちる — 復習間隔の計算、忘却予測、
リマインダーのスケジューリング。画面だけ見ていると欠落を見逃す。

**手順**: 理論の推奨サイクル 1 周分 (例: 学習 → 翌日復習 → 3 日後復習) を横軸に、
5 層を縦軸にした表を作り、空欄セルを列挙する。

## 6. DDD ユビキタス言語

ドメイン概念 → 画面 → 仕様 → 実装まで**同じ言葉**で表現されているかを確認する。

**例**: 題材が「アクティブリコール」なのに、画面では「テスト」、別画面では「クイズ」、
DB では「Exam」— 用語が 3 通りに揺れているのはドメイン理解が弱いシグナル。
テスト/Exam は「評価」の含意を持ち込み、想起練習という理論概念を誤解させる点で
単なる表記揺れより重い。

**手順**:
1. 手順 2 の正統用語集を基準にする
2. 画面表示名・仕様書・データモデル名・API 名を突き合わせる
3. 揺れ (同一概念に複数語) と 誤訳 (理論概念と含意の違う語) を分けて指摘する

コードが読める場合はデータモデル名まで見る。読めない場合は画面間の揺れだけでも検出できる。

## 7. ドメインヒューリスティック評価

通常のヒューリスティック評価 (一貫性・フィードバック・エラー防止) を、
**理論に合わせたドメイン固有の原則**へ拡張して各画面を採点する。

**手順**:
1. 手順 2 の原理から、UI が満たすべき原則を 4〜7 個定義する。
   例 (アクティブリコール系): 即時フィードバックがある / 自己説明を促す /
   振り返りを促す / 間違いを歓迎する (罰しない)
2. 各画面 × 各原則で 適合/部分適合/違反 を採点する
3. 違反セルを所見に落とす

原則の数を絞るのがコツ — 理論の中核だけに限定しないと採点が形骸化する。

## 8. Theory of Change

教育・社会プログラム評価の手法。**機能 → 行動変化 → 中間成果 → 最終成果**の
因果チェーンを明示し、各リンクが本当に成立するかを検証する。

**例**: 通知 → 復習率が上がる → 忘却率が下がる → 長期記憶になる → 学力向上。

**手順**:
1. 主要機能ごとに因果チェーンを 1 本書く
2. 各リンクについて「成立しない条件」を挙げる (通知が無視される、復習が再読になっている等)
3. プロダクトが逆方向の行動を促していないかを確認する
   (例: 連続ログインストリークが「毎日大量にやる」を促し、分散学習と逆行する)
4. 検証可能な指標があるか (復習実施率などを計測できる設計か) を確認する

**判定**: 因果が語れない機能は上向き orphan。因果が理論と逆向きの機能は Critical。
