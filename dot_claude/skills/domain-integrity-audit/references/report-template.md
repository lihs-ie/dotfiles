# 監査レポートテンプレート

SKILL.md 手順 6 で使う。セクションは省略しない (該当なしなら「該当なし」と書く)。
プロダクト全体監査用。単一機能の設計レビューでは「サマリー / トレース結果 / 因果仮説 / 判定」に縮約してよい。

```markdown
# ドメイン整合性監査: <プロダクト名>

## 1. 監査サマリー

- 対象理論: <理論名> (明示 / 仮置き)
- 結論: <2〜3 文。理論忠実度の総評>
- 所見件数: Critical N / High N / Medium N / Low N

## 2. 監査対象と入力素材

- 見たもの: <仕様書・スクショ・コード等>
- 見ていないもの: <レイヤー・画面。ここに関する所見は仮説である旨>

## 3. ドメイン理論の正規化

参照したドメイン専門知識 skill: <path> (既存 / 今回生成 / なし — インライン正規化)

| 要素 | 内容 |
|---|---|
| 原理 | |
| 前提条件 | |
| 必要な行動 | |
| 正統用語集 | |
| 因果チェーン | |
| 禁忌 | |

## 4. トレーサビリティ行列

| 原理 | 必要な行動 | 機能 | UI | 判定 |
|---|---|---|---|---|
| | | | | 支援あり / 部分支援 / 未支援 |

### orphan 一覧

- 下向き orphan (未支援原理): ...
- 上向き orphan (無根拠機能): ...
- 矛盾機能 (原理と逆方向に働く): ...

## 5. 8 レイヤー監査表

| 評価レイヤー | 確認すること | 判定 | 根拠 |
|---|---|---|---|
| ドメイン理解 | 理論の原則・前提条件を正しく整理しているか | ✅/⚠️/❌ | |
| 概念モデル | 理論の概念がアプリ内の概念・用語に反映されているか | | |
| タスク | 実践者がすべき行動が機能として支援されているか | | |

## 6. 所見 (severity 順)

### [Critical] <タイトル>
- 内容: <何がどの原理とどう矛盾/欠落しているか>
- 根拠: <素材のどこから読み取ったか>
- 使用フレームワーク: <RTM / ToC / ...>

(以下 High / Medium / Low)

## 7. 改善提案

所見ごとに 1 つ以上。理論のどの原理に沿わせるための変更かを添える。

## 8. 検証項目

監査では判定できず、実測・実使用で確かめるべき仮説のリスト
(例: 通知の実復習率への効果、ユーザーが復習を再読で済ませていないか)。
```
