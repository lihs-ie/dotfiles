# ドメイン専門知識 skill の生成手順とテンプレート

SKILL.md 手順 2-3 から参照される。プロジェクトごとに 1 ドメイン 1 skill を生成・永続化する。
生成された skill はこの監査だけでなく、そのプロジェクトの機能設計・レビュー・用語判断すべての
参照点になる — 監査の副産物ではなく、プロジェクトのドメイン知識の正本として書く。

## 生成手順

1. **ドメイン知識体系の特定** — プロダクトが明示する理論・メソッド・規範。明示がなければ
   プロダクトの主張 (「科学的に」「〜法準拠」等) から逆算し、仮置きであることを skill に明記する
2. **調査** — モデルの記憶だけに頼らず、一次文献・定評ある解説を優先して裏を取る
   (提唱者の原典、標準的な教科書、規格の原文)。WebSearch / Context7 / GitHub 検索を使う。
   出典は skill の末尾に残す — 後で知識を改訂するとき、どこまでが裏取り済みか分かるように
3. **正規化** — 下のテンプレートの各セクションを埋める
4. **保存** — 対象プロジェクトの `.claude/skills/domain-expertise-<slug>/SKILL.md`。
   `<slug>` は理論名の kebab-case (例: `domain-expertise-spaced-repetition`,
   `domain-expertise-progressive-overload`, `domain-expertise-double-entry-bookkeeping`)
5. **検収** — 次の 2 点を確認する:
   - 「必要な行動」が**実践者の言葉**で書かれているか。機能の言葉 (「通知を受け取る」「ボタンを押す」)
     で書くと、アプリの現状を理論と誤認して監査が循環する
   - 「禁忌」が具体的か。禁忌は監査で Critical (矛盾機能) を判定する基準になる —
     理論が何を**否定**するかが曖昧だと、最も重い所見が出せない

## テンプレート

```markdown
---
name: domain-expertise-<slug>
description: <プロジェクト名> が依拠する <理論名> の正規化知識。Use when このプロジェクトで機能設計・機能レビュー・ドメイン整合性監査・用語の判断・仕様の妥当性確認を行うとき。理論の原理・前提・実践者の行動・正統用語・因果チェーン・禁忌を提供する。
---

# <理論名> — ドメイン専門知識

<理論の 2〜3 行の要約と、このプロダクトがどの範囲で依拠しているか>

## 原理 (中核メカニズム)

- <原理 1>: <説明> (出典)
- <原理 2>: ...

## 前提条件 (理論が効く条件)

- <例: 想起練習であること — 再読では効果が大きく下がる>

## 必要な行動 (実践者がすべきこと)

機能ではなく行動で書く。

- <例: 忘れる前に復習する / 前回を少し超える負荷を選ぶ / 取引の都度、借方と貸方を記録する>

## 正統用語集

| 概念 | 正統な用語 | 誤用・混同されやすい語 |
|---|---|---|
| | | |

## 因果チェーン (Theory of Change)

<行動> → <中間成果> → <最終成果> の形で主要な因果を列挙する。

## 禁忌 (理論が明示的に否定する行動・パターン)

監査で Critical 判定の基準になる。理論の一次文献が否定しているものを優先する。

- <例: 一夜漬け (massed practice) — 分散効果の対偶。短期成績は上がるが保持率を毀損する (出典)>
- <例: 毎日の限界挑戦 — 回復を挟まない高強度連続は過負荷の漸進ではなく過労 (出典)>

## 出典

- <一次文献・教科書・規格へのリンク/書誌>
- 裏取り状況: <どこまで一次文献で確認済みか、モデル知識のみの箇所はどこか>
```

## 既存 skill の改訂

監査・設計中に知識の誤り・不足に気づいたら、その場で skill を改訂する (知識の正本は skill 側)。
改訂時は「出典」の裏取り状況も更新する。監査レポートには「参照したドメイン専門知識 skill:
<path> (既存 / 今回生成 / 今回改訂)」を明記する。
