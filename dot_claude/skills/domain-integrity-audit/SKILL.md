# Domain Integrity Audit (ドメイン整合性監査)

プロダクトを「**依拠するドメイン知識体系を忠実に実装しているか**」で評価する。
UI ユーザビリティ評価では「使いやすいが理論的に間違っている」プロダクトを検出できない —
例えば快適に使える一夜漬け支援機能は、スペースドリピティションの原理を積極的に毀損している。
対象ドメインは問わない: 学習理論、GTD、トレーニング理論、複式簿記、診療ガイドライン、
アクセシビリティ規格 — プロダクトが何らかの理論・メソッド・規範を掲げていれば監査できる。

役割分担: コード内部の DDD モデリングレビュー = `domain-modeling-review` /
実装が仕様書に従っているか = `spec-compliance-review` /
**プロダクト ↔ ドメイン理論の整合性 = この skill**。

## 二層構造

```
┌─ 監査エンジン (この skill)
│    ドメイン非依存の手順・8 フレームワーク・レポートテンプレート
└─ ドメイン専門知識 skill (プロジェクトごとに生成・永続化)
     対象理論の正規化知識: 原理 / 前提 / 行動 / 用語 / 因果 / 禁忌
```

分離する理由: 監査の質は理論理解の質で決まるが、理論はプロダクトごとに違い、
モデルの記憶だけでは深さも正確さも保証できない。理論の正規化を毎回の監査でやり直すと
浅い理解のまま監査に入りがちで、セッション間で理解が引き継がれない。
プロジェクト配下に skill として永続化すれば、監査・機能設計・レビュー・用語判断のすべてが
同じ正規化知識を参照でき、知識の改訂もそこに集約される。

## 監査の背骨: トレーサビリティチェーン

すべての判定は次のチェーンの**双方向トレース**に帰着する:

```
ドメイン理論 (原理・前提条件)
    ↓
必要な行動 (実践者がすべきこと)
    ↓
機能 (行動を支援するもの)
    ↓
画面・UI・ユーザーフロー
    ↓
効果の因果 (機能 → 行動変化 → 成果)
```

- **下向き orphan (未支援原理)**: 理論が要求する行動に対応する機能がない → 理論の欠落実装
- **上向き orphan (無根拠機能)**: どの原理にも遡れない機能 → ドメイン対応が弱い。
  理論と**矛盾**する機能はさらに重い (欠落ではなく積極的毀損)

「このボタンはどの原理を支えているのか?」に答えられなければ上向き orphan である。

チェーンの一例 (ドメインが変わっても形は同じ):

| ドメイン | 原理 | 行動 | 機能 | UI |
|---|---|---|---|---|
| 学習 (SRS) | 忘却曲線 | 忘れる前に復習 | スケジューラ + 通知 | レビュー画面 |
| 家計 (複式簿記) | 貸借平均 | 取引を借方/貸方で記録 | 仕訳入力 + 検算 | 仕訳画面 |
| 筋力 (漸進性過負荷) | 過負荷の漸進 | 前回を少し超える負荷 | 前回記録の提示 + 推奨負荷 | セット入力画面 |

## 手順

### 1. スコープ確定

- 対象プロダクトと、依拠するドメイン知識体系 (理論・メソッド・規範) を特定する
- 入力素材を確定する: 仕様書 / スクリーンショット / コード / 実使用。全部揃わなくてよいが、
  **何を見て何を見ていないかをレポートに明記する** (見ていない層の所見は仮説として出す)
- 理論が明示されていない場合 (「効率的に学べる」等の暗黙の主張のみ) は、主張から逆算して
  最も近い確立理論を仮置きし、仮置きであることを明記する

### 2. ドメイン専門知識 skill の解決 (なければ生成)

1. 対象プロジェクトの `.claude/skills/` に `domain-expertise-<ドメイン名>` があるか確認する
2. **あれば**それを読み、正規化知識 (原理 / 前提 / 行動 / 用語 / 因果 / 禁忌) を監査の基準にする。
   監査中に知識の誤り・不足に気づいたらその skill を改訂する (知識の正本はあくまで skill 側)
3. **なければ** [references/domain-expertise-skill-template.md](references/domain-expertise-skill-template.md)
   の手順で生成する: 一次文献を調査 → テンプレートへ正規化 → 対象プロジェクトの
   `.claude/skills/domain-expertise-<slug>/SKILL.md` に保存。以後の監査・設計・レビューが再利用する
4. 保存先プロジェクトがない場合 (競合アプリの単発分析等) は、正規化結果をレポートの
   「ドメイン理論の正規化」セクションに直接書く (揮発でよい)

**理論の誤解に基づく監査は監査自体が無効になる** — ここが最も手を抜いてはいけない工程。
「このプロジェクトのドメイン専門知識 skill を作って」と、この手順だけを単独で頼まれることもある。

### 3. プロダクトインベントリ

素材からプロダクト側の実態を列挙する:

- 概念・用語 (画面表示名だけでなく、データモデル名・API 名まで取れるなら取る)
- 機能一覧
- 画面と導線
- ユーザーに見えない層: 通知・バッチ・スケジューラ・システム処理 (Service Blueprint 視点。
  理論の要求はしばしば見えない層に落ちる — 例: 復習間隔の計算、仕訳の貸借検算)

### 4. トレーサビリティ行列

原理 × 機能の行列を作り、双方向にトレースする。

- 各原理について: それを支える行動 → 機能 → UI が存在するか (下向き)
- 各機能について: どの原理に遡れるか (上向き)
- orphan を両方向で列挙し、矛盾機能 (原理と逆方向に働く機能、専門知識 skill の「禁忌」に
  該当する機能) は別枠で明示する

### 5. フレームワーク別検査

行列で見つかった疑義を裏取りするために、該当するフレームワークを選んで深掘りする
(全部やる必要はない)。各フレームワークの手順と例は [references/frameworks.md](references/frameworks.md) を読む。

| 疑義 | 使うフレームワーク |
|---|---|
| 用語が理論とずれている / 画面間で揺れている | Conceptual Model Alignment + DDD ユビキタス言語 |
| 推奨プロセスを迷わず実践できるか怪しい | Cognitive Walkthrough + Task Analysis |
| 見えない層 (通知・バッチ) の欠落 | Service Blueprint |
| 機能が成果につながるか怪しい | Theory of Change |
| 画面ごとに理論の原則を採点したい | ドメインヒューリスティック |

### 6. レポート

[references/report-template.md](references/report-template.md) の構造で出力する。
**8 レイヤー監査表** (ドメイン理解 / 概念モデル / タスク / ユーザーフロー / 機能 / UI /
効果の仮説 / トレーサビリティ) を必ず含める。所見には severity をつける:

| Severity | 基準 |
|---|---|
| Critical | 理論と矛盾する機能・導線 (積極的毀損、専門知識 skill の「禁忌」に該当) |
| High | 中核原理が未支援 (下向き orphan) |
| Medium | 用語不整合・周辺的な行動の未支援・上向き orphan |
| Low | 改善余地・より理論に沿う代替案がある |

## 新機能提案の設計レビューとして使う場合

プロダクト全体ではなく単一の機能提案を審査するときは、手順 2 (専門知識 skill の解決) を
済ませた上で手順 4 をその機能 1 つに絞って実行する:

1. この機能はどの原理に遡れるか
2. 実践者のどの行動をどう変えるか
3. 理論の原理・前提・禁忌と矛盾しないか (促す行動が理論の禁じる行動になっていないか)
4. 「機能 → 行動変化 → 成果」の因果仮説は何か。検証方法はあるか

矛盾の典型例: 分散学習が原理のアプリに「一夜漬けモード」を足す、
回復が原理のトレーニングアプリに「毎日自己ベスト更新チャレンジ」を足す、
GTD アプリに Inbox を経由しないタスク直接実行導線だけを足す — いずれも単体では便利だが理論を毀損する。
