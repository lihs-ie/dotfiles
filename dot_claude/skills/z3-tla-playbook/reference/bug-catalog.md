# バグ型カタログ — 対象領域を当てるためのチェックリスト

実装から仕様を吸い出すと繰り返し出る型。**「ありそう」を先に当てて対象領域を選ぶ**ために使う。
台帳 (`ledger.md`) では ID (`Z-01` 等) で参照する。

> 出典: mizchi「実装コードから仕様を吸い出して Z3 / TLA+ でバグを払い出す — 実践プレイブック」
> <https://gist.github.com/mizchi/db7817e6fc077d567c41cd9d41bb1c53> (2026-07-25 参照)。
> 本ファイルは上記の分類を、この環境のハーネスで扱えるよう ID 付きチェックリストに再構成した派生物。

---

## Z: 純粋述語・設定系 (Z3 向き — 全入力に対して、ある一瞬)

| ID | 型 | 症状 | 見つけ方 |
|---|---|---|---|
| Z-01 | 矛盾設定 (dead config) | 条件の連言が充足不能。どんな入力でも通らない (「A のみ ∧ A を除外」「開始 > 終了」「x>20 ∧ x<18」) | 設定そのものを `Solver` に入れて `unsat` なら dead。`reachable(..., "LIVE")` が落ちる |
| Z-02 | 冗長・内包 (subsumption) | 片方が他方を含意し、設定されているのに効いていない (「上限10回 ∧ 上限1回」) | `Implies(a, b)` の否定が `unsat` なら b は死に設定。「実効値」を算出して警告する |
| Z-03 | 被覆の穴 / dead branch | どの選択肢にもマッチしない入力がある / どの入力でも選ばれない枝がある | 全枝の論理和の否定が `sat` → 穴。各枝単独が `unsat` → dead branch |
| Z-04 | 変更の差分影響 | 設定を編集したとき「誰の判定が変わるか」が読めない | `predict_old(x) != predict_new(x)` を `sat` で解き、反転する入力を記号的に摘出する |
| Z-05 | 表現の等価性 | 旧形式↔新形式、リファクタ前後が同じ意味か不明 | `old(x) != new(x)` が `unsat` なら全入力で等価。移行・リファクタの回帰ガードになる |

## T: 並行・時間系 (TLA+ 向き — 時間を通じて、全順序・全 interleaving)

| ID | 型 | 症状 | 見つけ方 |
|---|---|---|---|
| T-01 | read-modify-write レース / TOCTOU | 読んで判定して書くが分離しており、同時実行で両者が古い値を読み両方通る (上限超過・二重処理) | 判定と書き込みを別ステップに分けたモデルと、条件付き書き込み (atomic) のモデルを**対比**する |
| T-02 | 判定と記録の分離 | 判定は即時、記録は非同期。判定時点で記録がまだ無く上限をすり抜ける | 記録アクションを遅延可能な独立ステップとしてモデル化する |
| T-03 | 結果整合 (staleness) | 書いた値が読み手に見えるまでの遅延だけで、**並行が無くても**上限が破れる | 読み手が見る値を「過去のいずれかの版」に非決定化する |
| T-04 | 原子性 / torn read | 共有リソース (ファイル・スナップショット) の途中状態を読む | 「別ファイルに書いて rename (atomic)」vs「in-place 上書き」を対比する |
| T-05 | カウンタの不変条件 | 重複配信・並行下でカウンタが負になる / ガード条件が必要十分でない | `NeverNegative == c >= 0` を名前付き invariant にする |
| T-06 | 収束 / runaway (停止性) | 引き上げ・リトライのループが有界回で止まらない。外部条件 (期限) だけが唯一のブレーキ | 停止条件を外した変種を回し、その条件が load-bearing かを確かめる |
| T-07 | 伝搬 / 最終整合 | commit した変更がいつか必ず反映されるか。crash+再起動で更新が失われないか | edge-trigger は失いうる / level-trigger は追いつく、を別モデルで対比する |
| T-08 | 冪等性 | リトライで二重カウント。ID 生成が「送信毎ランダム」だと重複記録 | 同一操作の再送を Next に加え、invariant が保たれるか見る |

## B: 境界・信頼系 (どちらでも)

| ID | 型 | 症状 | 見つけ方 |
|---|---|---|---|
| B-01 | fail-open / fail-close の非一貫 | 情報が取れないとき、ある機構は全落ち、別の機構は素通り | 「エラー時にどう振る舞うか」を機構ごとに列挙して表にすると不整合が見える |
| B-02 | エラーを boolean に畳む × 否定 | 「不一致」と「エラー」を同じ false に畳む実装に否定 (NOT/inverse) をかけると、**エラー時にマッチに化ける**。壊れた入力ほど通る | 3 値 (match / no-match / error) でモデル化し、否定演算を通した後の値を検査する。**最も見落とされやすい** |
| B-03 | 空集合の意味 | 空の AND=真 (常時マッチの backdoor)、空の OR=偽、要素ゼロ=真 が階層で不整合 | 空コレクションを定義域に必ず含める |
| B-04 | 信頼境界と詐称 | ユーザーが自由に付けられる入力 (クエリ param・ヘッダ) が検証を経ず「信頼された値」として採用される | 値の決定経路を優先順位付きで列挙し、無検証採用が上位に無いか見る |
| B-05 | クロス境界の表現契約 | 2 システムが同じビット列/enum/レイアウトを共有するが、片方が hourly・片方が 15 分、MSB-first vs LSB-first | 展開・変換の全単射性を `unsat` で証明する (Z-05 と同型) |
| B-06 | クライアント側だけの検証 | UI/フロントだけが弾き、サーバー/API は素通し → API 直叩きで不正状態が作れる | サーバー側の述語のみで invariant が保てるかを検査する |
| B-07 | 欠けた前提条件 | 負のサイズ・空配列で panic。ガードが呼び出し側にしか無い | 定義域を「呼び出し側の保証」抜きで広げて反例を探す |

---

## 使い方

1. 対象領域を選ぶ前に、この表で **どの型がありそうか** を 2〜3 個当てる
2. 当てた型を `ledger.md` の A 欄 (実装の主張) に ID 付きで書く
3. Z 型なら Z3、T 型なら TLA+、B 型はどちらか近い方を選ぶ (`SKILL.md` の判定フロー参照)
4. **状態空間が有限かつ決定的なら、ツールを持ち出す前に素の全列挙が一番安い**
