# 吸い出しの視点 — コードから仕様を抜くとき何を見るか

実装を読むとき **「宣言された仕様」と「暗黙の挙動」を必ず分けて** メモする。
分けないと、惰性で決まった挙動を「仕様」として固定してしまう。

> 出典: mizchi「実装コードから仕様を吸い出して Z3 / TLA+ でバグを払い出す — 実践プレイブック」
> <https://gist.github.com/mizchi/db7817e6fc077d567c41cd9d41bb1c53> (2026-07-25 参照)。
> 本ファイルは上記の観点を作業用チェックリストに再構成した派生物。

---

## 1. 宣言された仕様の在り処 (intent が書かれている場所)

| 場所 | 見るもの | 注意 |
|---|---|---|
| コメント | 特に「なぜ」を語るもの (`// 〜のときは全部OK`, `// 溢れないかチェック`) は仕様の宣言 | 「元のコードがそうなっていた」「理由は分からない」系は **化石 (fossil)** の印。仕様か惰性か要確認 |
| テスト名・アサーション | `NG if count equal the cap` のようなテスト名は境界仕様そのもの | 期待値の並びも仕様。ただし実装追認テストの可能性を疑う |
| ガード節・panic・error 返し | 前提条件と fail-mode の宣言 (`if n < 0 { ... }` の有無) | ガードが呼び出し側にしか無いなら B-07 |
| enum 定義・定数テーブル・スキーマ制約 | 取りうる値と、値↔意味の対応 | 2 システム間で共有していれば B-05 |

## 2. 暗黙に決めている挙動 (どこにも書いてないが実装が確定させている)

- **default 値・空/nil の扱い** — 未設定が「全許可」か「全拒否」か。empty collection の真偽 (→ B-03)
- **エラー時の分岐** — missing / parse 失敗 / タイムアウトで true/false/例外 のどれに倒れるか (→ B-01, B-02)
- **順序依存と短絡** — 適用順で結果が変わるか (副作用があるか)、短絡が結果に効くか理由コードだけか
- **値が「決定される」場所** — フォールスルーの優先順位、複数ソースからどれを採るか、信頼判定の位置 (→ B-04)
- **クロス境界の変換** — シリアライズ / ビットレイアウト / 単位 / タイムゾーン / 曜日始まり (→ B-05)
- **誰が制御できる入力か** — infra が付ける値 vs ユーザーが自由に付けられる値 (信頼境界)

## 3. 機械的に投げる 8 つの問い

各述語・各機構に対して、順に投げる。答えをそのまま台帳 A 欄に書く。

1. **空/未設定のとき何が起きる?**
2. **エラー/取得失敗のとき true か false か例外か?** (fail-open / fail-close)
3. **否定 (NOT/除外/inverse) をかけると、上の答えはどう化ける?** ← B-02 はここでしか出ない
4. **境界はどっち向き?** (`>` か `>=` か、端点を含むか)
5. **同時に 2 つ来たら?** 片方の結果がもう片方に間に合うか?
6. **この値は誰が決める?** 信頼できない相手が差し替えられるか?
7. **このループ/引き上げは何で止まる?** 止めているのは本質的な条件か、たまたまか?
8. **2 つのシステムがこのデータで合意しているか?** (レイアウト・enum・単位)

## 4. 抜いたものをモデルに落とす

- **決定関数を純粋に切り出す** — 観測可能な入力 → 結果 の純粋関数 `predict(state)` を、実装の配管
  (I/O, フレームワーク, DB) を剥がして書く。これが仕様の数学的表現になる。
- **肯定的・決定的・ドメイン語で宣言する** — 「〜のとき 5xx を返さない」のような否定的ガードと、
  「こう操作したらこう結果になる」という振る舞い仕様を分ける。振る舞い仕様は実装の内部語彙を隠し、
  ドメインの言葉だけで読めるようにする。
- **invariant に名前を付ける** — `NeverOverCap == served <= cap` のように。名前が付くと
  レビューで「この性質は満たす?」と会話できる単位になる。
- **反例志向で書く** — 期待を invariant として主張し、ツールに否定させる。**成立を証明したいのか、
  反例が欲しいのか**を意識して立てる。
- **同値類と境界を列挙する** — 全入力は無限でも、判定が変わる同値類と境界は有限。
  境界 (`cap-1`, `cap`, `cap+1`) は必ず定義域に入れる。
